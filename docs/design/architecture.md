# Architecture: layering, money, shares, currencies

_The cross-cutting representation rules. CLAUDE.md states them in brief; this is the full reasoning._

## Architecture

**Backend layering** (`internal/`): requests flow `router → handlers → db → models`. The `db.DB` wraps a `*gorm.DB`; it is created once in `main.go` via `db.Open(dsn)` (which opens the DB and runs `AutoMigrate`) and injected into handlers. String UUID primary keys are generated by the handlers (`uuid.NewString()` when building the model on create), not by the db layer. Handlers never touch GORM directly. The db layer translates GORM's `gorm.ErrRecordNotFound` into the sentinel `db.ErrNotFound`, which `handlers.respondDBError` (in `common.go`) maps to 404; `models.ErrInsufficientShares`, `db.ErrConflict`, `db.ErrSymbolTaken` and `db.ErrInstrumentInUse` map to 409; anything else becomes a 500. The connection pool is capped at a single connection (`SetMaxOpenConns(1)` in `db.Open`) because SQLite allows only one writer at a time.

**Money is integer minor units everywhere.** Every monetary field (`price`, `fee`, `net_amount`, `last_price`, `cost_basis`, `realized_pl`) is `int64` hundredths, never a float. The API speaks minor units; the frontend converts at the UI edge via `frontend/src/money.ts`.

**Share counts follow the same rule, scaled rather than whole.** `Quantity` is `int64` in `models.SharesScale` units (a millionth of a share), so 2.79 shares is stored as `2_790_000`. Fractional shares are real — a broker filling a fixed-amount purchase hands you a fraction of one — and a float count would drift the way a float cent would, compounding through every cost basis built on it. A millionth is finer than any broker reports, so nothing is truncated on the way in. `frontend/src/shares.ts` converts at the UI edge; **never divide a quantity by hand**, and never multiply one by a price without `models.Gross`, which is the only place the scale is divided back out.

**There is no FX rate anywhere, so amounts in different currencies are never added.** `Instrument.Currency` is `TWD` or `USD`, defaulting from the market (`models.DefaultCurrencyForMarket`) and overridable at creation. `GET /positions/summary` therefore returns a **slice** of `db.CurrencySummary`, one per currency the user holds, never a single grand total — summing a TWD cost basis with a USD one produces a number that means nothing. The frontend renders one card block per currency side by side. A currency becomes **locked once trades exist** against the instrument (`db.ErrCurrencyLocked` → 409): every price and cost basis recorded under it is denominated in the old currency, so switching would reinterpret the whole history rather than correct it. Instruments predating the column are backfilled from their market in `db.Open`, because an empty currency would silently drop those holdings out of every total.

## Conventions

- Adding a backend resource means touching all layers: model in `internal/models` (with GORM tags, and registered in the `AutoMigrate` call in `db.Open`), CRUD methods on `db.DB`, a handler struct with a `New*Handler(s *db.DB)` constructor, and route registration in `internal/router/router.go`.
- Migrations are automatic (`AutoMigrate` on startup), which adds columns/tables but does not drop or alter existing ones; destructive schema changes must be handled manually. A change of *units* is one of those: `db.scaleShareCounts` multiplies every stored quantity when share counts became scaled, and **must run exactly once** — nothing in the data says whether it already has, since `100` is a plausible number of whole shares and a plausible 0.0001 of one. `models.SchemaMeta` holds the marker that decides, rather than a heuristic; running the backfill twice would multiply every holding by a million with no way back.
- CORS is permissive (`internal/router/router.go`) for local dev; tighten before any real deployment.
- `main.go` runs the server under `http.Server` with signal-driven graceful shutdown (SIGINT/SIGTERM → `Shutdown` with a 10s drain → `db.Close`). `GET /health` calls `db.Ping` so it reflects DB connectivity, and reports `started_at`, `uptime` and `revision`. Those exist to answer "is the server running the code I just wrote?" — `go run .` does not reload on edit, and a stale process serving an old contract is indistinguishable from a bug in the new one until you can see it started before the change. `revision` is only stamped for built binaries, so `started_at` is the signal to trust.
- Code comments and all user-facing strings are in English.

## Deliberately out of scope

Cash balances and buying power, FX rates and cross-currency totals (currencies are tracked and reported separately, never converted), FIFO/specific-lot cost basis, **stock** dividends, splits and reverse splits (they invalidate every historical share count — a good exercise, but a step up in complexity; *detection* is built, on exactly the terms `DividendEvent` set — see **Splits** — so what is out of scope is adjusting a book, never noticing that one needs it), automatic dividend *posting* (detection is built — see `models.DividendEvent` — but an entry is never written without the user), estimating what is withheld from a dividend (a different charge from a brokerage commission, with rates that depend on the holder rather than the trade), and multiple portfolios per user.

The **earnings calendar** — when a company next reports — is a different case: it is not declined but unavailable. It lives in Yahoo's `quoteSummary` modules, which now answer 401 without a cookie and a crumb, and no other free source this system already talks to carries it. Anyone adding it is buying a session-management dependency, not writing a feature.

The moving-average choice in particular is load-bearing: FIFO would require a lot table and consumption logic, and would change invariants 1 and 2 substantially.
