# Price history

_Read before changing `DailyClose`, the history sync, or `EarliestHistoryNeeded`._

## Price history

`Instrument.LastPrice` answers "what is it worth now?"; `models.DailyClose` answers "what was it worth then?", which is what any figure spanning time has to consult. The two are kept apart because they are maintained differently — a quote is refreshed against the provider's latest, while a close describes a session that is over and does not change.

`DailyClose.Date` is the calendar day as **YYYY-MM-DD, not a timestamp**: a daily bar belongs to a session rather than an instant, so a time would invite comparisons that depend on the reader's zone, and as a string it sorts lexicographically into chronological order. The composite primary key `(instrument_id, date)` is what makes a refetch idempotent — `db.SaveDailyCloses` upserts, so the same session fetched twice updates one row instead of accumulating duplicates that would each be counted.

`quotes.Client.History` shares `chart()` with `Fetch`, so there is still exactly one place that knows how to talk to the provider. `quotes.barDate` names the session a bar belongs to by taking the **UTC date of the provider's timestamp**, which works only because every market this system addresses opens after midnight UTC (Taipei 01:00, New York 13:30/14:30). A market opening earlier would break it, and none of the supported ones does. A bar the provider reports as null is skipped rather than read as 0 — recording a stock as worthless for a day is exactly the kind of thing every consumer downstream would believe.

`POST /api/v1/instruments/sync-history` is open to any authenticated user on the same terms as the quote refresh, and rate-limited harder (2/min) because a first run downloads years. **Only instruments something needs are fetched, and only from the day it first needed them** (`db.EarliestHistoryNeeded`) — earlier prices value nothing, and an instrument nobody trades or plans to has nothing to plot, which is what keeps a run proportional to the book rather than to the master data. "Needs" is the first trade **or the start of a savings plan, whichever came first**, and the second half is not an optimization: a plan comes due on dates of its own and its prompt estimates the shares from that day's close, so a plan set up before its first purchase — the ordinary way to start one — was skipped entirely by the first-trade rule and could never offer an estimate. Runs are incremental: an instrument already holding history is topped up from `historyOverlap` before its last session, because the provider revises a close occasionally and the most recent bar can be provisional. **A series that already starts later than what needs valuing is refetched whole instead**, and that branch is load-bearing rather than an optimization: the top-up reaches back from the *last* stored session, so on its own it can only extend a series forward and will never fill a gap at the front — pressing Sync does nothing at all while the report goes on saying prices are missing. That was harmless while only an instrument's own first trade could set the needed start, since that date never moves earlier. A benchmark breaks it: it reaches back to the first trade of the *book* it measures, usually long before the benchmark itself was bought, so every already-traded holding chosen as one was stuck. A back-dated trade does the same to an ordinary holding. `db.EarliestStoredClose` is what the branch consults, and the gap has to exceed `historyOverlap` to bite — which is why a test with a few days between the two dates passes either way. A partial failure is not an error for the run, exactly as in a quote refresh, and a series in the wrong currency is a failure rather than a price.

**A curve that has fallen behind is topped up on arrival.** Every figure on `/reports` and a holding's chart is valued at stored closes while Holdings values at the live quote, so a week without pressing Sync made the two pages disagree with nothing but a small "latest" date to say why. `frontend/src/historyLag.ts` measures how far the last stored session trails whichever comes first, the period's end or today (a report on a past year is complete, not stale), and more than `STALE_AFTER_DAYS` (3 — a weekend plus the overnight gap to a Taipei morning is ordinary) counts as behind. Reports and an open holding's page then run the history sync once, quietly, under a shared `claimAutoRun('history', 30 min)` so moving between them does not ask twice. It is **triggered by the lag, not by arrival** — unlike the quote refresh on Holdings — because the history sync has no server-side freshness window and every run asks the provider once per instrument. When the top-up fails or the provider has nothing newer, a notice above the chart says how many days the figures stop short. A sold holding is not measured: its chart may simply end where the position did.
