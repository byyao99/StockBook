# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

**StockBook** — a personal portfolio ledger: a Go + Gin REST API (repo root) serving **Instrument**, **Transaction** and **Position** resources, plus a Vue 3 + TypeScript SPA (`frontend/`) that consumes it. Users record trades that already happened; the system derives holdings, moving-average cost, and realized/unrealized profit and loss. There is no cash balance, no order matching, and no broker integration — it is a book of record, not a trading system.

Persistence is SQLite via GORM, using the pure-Go driver `github.com/glebarez/sqlite` (no cgo). The DB file path defaults to `stockbook.db` and is overridable with the `DB_PATH` env var.

## Commands

Backend (run from repo root):

```bash
go run .                    # start API on :8080 (PORT env var overrides)
go build ./...              # build
go vet ./...                # vet
go test -race ./...         # run the test suite — ALWAYS with -race, see below
```

Backend env vars: `PORT` (default 8080), `DB_PATH` (default `stockbook.db`), `AUTH_SECRET` (HMAC key for bearer tokens — if unset a random key is generated at startup, so tokens do not survive a restart; set it in any real deployment), and `ADMIN_USERNAME`/`ADMIN_PASSWORD` (when both set and no users exist yet, an admin account is seeded on startup).

Frontend (run from `frontend/`):

```bash
npm install
npm run dev                 # Vite dev server on :5173, proxies /api -> :8080
npm run build               # vue-tsc --noEmit type-check, then vite build
npm run type-check          # type-check only
npm test                    # vitest unit tests (npm run test:watch for watch mode)
```

To work on the full stack, run the backend and `npm run dev` simultaneously; the Vite proxy (`frontend/vite.config.ts`) forwards `/api/*` to the backend, so the SPA uses same-origin relative URLs.

**Testing & CI.** `go test -race ./...` — the `-race` flag is not optional here. The concurrency tests in `internal/handlers/concurrency_test.go` are the ones that justify the compare-and-swap in the position write path, and without the race detector they are close to meaningless. Frontend tests are Vitest units colocated with their modules (`src/*.test.ts`) covering `money.ts`, `session.ts`, and `positionMath.ts` — the last is the contract test mirroring the backend's valuation rules, so changing how a position is valued means updating `internal/db/positions.go`, `positionMath.ts`, and that test together. Tests run in a plain node environment; `frontend/vitest.setup.ts` stubs `localStorage`. There are no component tests yet; adding some means switching `test.environment` in `vite.config.ts` to a DOM implementation. CI (`.github/workflows/ci.yml`) runs on pushes to master and PRs.

## Architecture

**Backend layering** (`internal/`): requests flow `router → handlers → db → models`. The `db.DB` wraps a `*gorm.DB`; it is created once in `main.go` via `db.Open(dsn)` (which opens the DB and runs `AutoMigrate`) and injected into handlers. String UUID primary keys are generated by the handlers (`uuid.NewString()` when building the model on create), not by the db layer. Handlers never touch GORM directly. The db layer translates GORM's `gorm.ErrRecordNotFound` into the sentinel `db.ErrNotFound`, which `handlers.respondDBError` (in `common.go`) maps to 404; `models.ErrInsufficientShares`, `db.ErrConflict`, `db.ErrSymbolTaken` and `db.ErrInstrumentInUse` map to 409; anything else becomes a 500. The connection pool is capped at a single connection (`SetMaxOpenConns(1)` in `db.Open`) because SQLite allows only one writer at a time.

**Money is integer minor units everywhere.** Every monetary field (`price`, `fee`, `net_amount`, `last_price`, `cost_basis`, `realized_pl`) is `int64` hundredths, never a float. The API speaks minor units; the frontend converts at the UI edge via `frontend/src/money.ts`. Share counts are whole `int` — there are no fractional shares.

**There is no FX rate anywhere, so amounts in different currencies are never added.** `Instrument.Currency` is `TWD` or `USD`, defaulting from the market (`models.DefaultCurrencyForMarket`) and overridable at creation. `GET /positions/summary` therefore returns a **slice** of `db.CurrencySummary`, one per currency the user holds, never a single grand total — summing a TWD cost basis with a USD one produces a number that means nothing. The frontend renders one card block per currency side by side. A currency becomes **locked once trades exist** against the instrument (`db.ErrCurrencyLocked` → 409): every price and cost basis recorded under it is denominated in the old currency, so switching would reinterpret the whole history rather than correct it. Instruments predating the column are backfilled from their market in `db.Open`, because an empty currency would silently drop those holdings out of every total.

### The five invariants

These are the things most easily broken by a well-meaning change. Each has tests pinning it down.

**1. `Position.CostBasis` is the total remaining cost, never a per-share average.** Storing an average would accumulate rounding error on every single trade: 3 shares at $10.00 plus 1 at $10.01 average 1000.25 cents, which is not an integer. Storing the total keeps `CostBasis` exact because it only ever gets added to and subtracted from. The average is derived for display at the UI edge (`averageCost` in `positionMath.ts`) and never persisted or returned by the API. Do not add an `average_cost` column or response field.

**2. Replaying the ledger is the definition of a position; the `positions` table is a cache of it.** `db.ReplayPosition` folds a user's transactions through `models.PositionState.Apply` in `ledgerOrder` and is the authoritative answer. `syncPosition` may take an incremental shortcut — applying just the new entry to the current row — but **only** when that entry sorts last in the ledger. An edit, a delete, or a back-dated entry landing mid-history always triggers a full replay, because moving-average cost is order-dependent and a single incremental step would compute the basis against the wrong prefix. `TestMaterializedPositionMatchesReplay` checks both paths agree across a table of sequences; any new write path must be added to it.

**3. The ledger's sort key is the triple `(traded_at, created_at, id)`.** Chronology alone is not a total order — several trades on the same day would fold in an arbitrary order and the average cost would drift between replays. `created_at` breaks same-day ties and `id` breaks same-tick ties. `isLastInLedger` compares the full triple, which is why an entry created in the same clock tick as another correctly falls back to a replay.

**4. Position writes are compare-and-swap, never read-then-write.** `writePosition` conditions its UPDATE on the `(quantity, cost_basis, realized_pl)` triple read a moment earlier — that triple is the row's version. Zero rows matched means somebody else moved it, which surfaces as `db.ErrConflict` → 409 rather than a silent overwrite. A plain conditional UPDATE (the `SET stock = stock - ? WHERE stock >= ?` trick an inventory system can use) is **not** available here: a sell releases cost in proportion to the shares leaving, so the new value depends on the old one in a way SQL arithmetic cannot express. For a holding that does not exist yet, the unique index on `(user_id, instrument_id)` turns a concurrent double-insert into the same conflict. `internal/db/cas_test.go` drives the guard directly, because the handler-level concurrency tests would otherwise pass on SQLite's single-writer serialization alone and prove nothing.

**5. Server-authoritative amounts, snapshotted symbols.** `Transaction.NetAmount` is always computed by `models.NetAmount` from quantity, price and side; a client-supplied value is ignored. `Transaction.Symbol` is snapshotted from the instrument at entry time, so renaming an instrument never rewrites history. `db.CreateTransaction` resolves the instrument inside its own transaction so it cannot be deleted between validation and the write.

### Moving-average cost

The whole algebra lives in `models.PositionState.Apply` (`internal/models/position_state.go`), which is pure and has no database dependency:

```
BUY(q, price, fee):   qty += q;  cost += q*price + fee
SELL(q, price, fee):  requires qty >= q
                      costRemoved = round(cost * q / qty)   // half-up, integer only
                      realized   += (q*price - fee) - costRemoved
                      cost       -= costRemoved
                      qty        -= q
```

Buy fees join the cost basis; sell fees come off the proceeds and so reduce the realized gain. A full exit needs no rounding at all (`cost*q/q == cost`), so `CostBasis` lands on exactly 0 with no residue — `TestApplyFullExitLeavesNoResidue` is the most sensitive check that the proportional math is right, and it is worth keeping green above almost anything else here.

### Unknown is not zero

An instrument's `LastPrice` is a `*int64` maintained by hand; nil means no quote has been set. Everything downstream reports that honestly rather than substituting zero: `PositionView.MarketValue` and `UnrealizedPL` are nil, `positionMath.ts` returns `null`, and the UI renders an em dash. `PortfolioSummary` goes further — its valuation totals cover only the priced holdings, so it reports `PricedCostBasis` alongside them (making `TotalUnrealizedPL == TotalMarketValue - PricedCostBasis` an identity that always holds) and `PricedPositions` vs `OpenPositions` so the UI can say how much of the book the totals actually account for. Showing an unvalued holding as $0.00 would read as a total loss; do not "simplify" these to zero.

### Fetching quotes

`internal/quotes` fetches prices from Yahoo Finance's undocumented chart endpoint (no API key, no official support — it has broken before). `quotes.Ticker` maps `(symbol, market)` to the ticker Yahoo knows: `.TW` for TWSE, `.TWO` for TPEX, bare for NYSE/NASDAQ, and nothing for `OTHER`. Nothing outside that package knows where prices come from, so replacing the provider is a one-file job.

`POST /api/v1/instruments/refresh-quotes` (admin) drives it. It is a deliberate, caller-triggered action rather than a background ticker, because **a background job has nowhere to return errors to** — a failed symbol would land in a log nobody reads. The endpoint returns 200 with a per-instrument result (`updated` / `skipped` / `failed`), each failure carrying **the provider's own wording** ("No data found, symbol may be delisted"), which is the only actionable diagnostic for a bad ticker. A partial failure is not an error for the run: one delisted symbol must not stop the other twenty from updating. To schedule it, point cron at the endpoint.

Two rules protect the book from the provider:

- **A failed fetch changes nothing.** The instrument keeps its previous quote *and its previous timestamp*, so the staleness rendered by `quoteAge()` in the UI stays truthful. Restamping a failed refresh would make a stale price look fresh; writing a zero would make it look worthless.
- **A currency mismatch is a failure, not a price.** If the provider quotes an instrument in a currency the book does not have on file, the fetch is reported as failed and nothing is written — adopting it would reinterpret every cost basis already recorded. Only an instrument with *no* currency yet adopts the provider's (`db.SetInstrumentCurrency`, which refuses to overwrite).

Stored quotes carry the **market timestamp the provider reported**, not the moment of the request (`db.UpdateInstrumentPrice` takes an `asOf`), so age shown to a user is the price's own age. Hand-entered quotes pass nil and are stamped now.

`router.New` takes a `handlers.QuoteFetcher`; it may be nil, in which case the refresh endpoint reports that quote fetching is not configured. Tests pass a stub — **no test ever reaches the network**, and `internal/quotes/yahoo_test.go` serves recorded payloads from an `httptest.Server`.

**Deletes and edits can be refused.** Removing a buy that a later sell drew on punches a hole in history: the replay hits `ErrInsufficientShares`, the whole transaction rolls back, and the API returns 409 with a message naming the offending entry (`insufficient shares: sell 1000 2330 on 2026-07-03`). Shrinking a buy below what a later sell consumed is refused the same way. This is the payoff of the replay architecture — the ledger can never be left in a state its own rules reject.

**List endpoints are paginated and sortable.** All list endpoints take `?limit` (default 20, max 100), `?offset`, `?sort`, and `?order`, parsed by `handlers.parseListOptions` into a `db.ListOptions`. Response shape is `{"data": [...], "pagination": {limit, offset, total}}`; single resources are `{"data": ...}` and errors `{"error": "..."}`. **Sorting is SQL-injection-safe by construction:** `db.orderClause` only emits a column name present in a per-resource allowlist (`instrumentSortColumns` / `transactionSortColumns` / `userSortColumns`), else falls back to the default. The position list spans a join, so it has its own `positionSortColumns` mapping sort keys to *qualified* column names — needed both to disambiguate `updated_at` (present on both tables) and as the same injection guard. Never interpolate `ListOptions.Sort` into a query directly.

**Authentication & authorization.** Accounts live in a `users` table (bcrypt `PasswordHash`, `Role` of `user`/`admin`). `internal/auth` provides bcrypt helpers and a `Manager` that issues/verifies bearer tokens — base64url JSON claims joined by `.` to an HMAC-SHA256 signature (key from `AUTH_SECRET`). Signature/expiry checks are stateless, but `middleware.authenticate` then loads the account from the DB (via the `middleware.UserSource` interface) and requires that it still exists and that the token's `token_version` claim matches `User.TokenVersion` — so deletions, role changes and password changes take effect immediately. The identity placed in the Gin context comes from the DB record, not the token claims. `POST /api/v1/auth/register` always creates a **user** (clients can never self-assign a privileged role); `POST /api/v1/auth/login` is rate-limited per client IP (10/minute, in-memory fixed window, per-process). Admin-only `/api/v1/users` endpoints provision, list, re-role and delete accounts; an admin cannot change or delete their own account, so they cannot lock themselves out.

**Route gating** (`internal/router/router.go`):

| Routes | Access |
|---|---|
| `GET /instruments`, `GET /instruments/:id` | any authenticated user (needed to enter a trade) |
| `POST/PUT/DELETE /instruments/:id`, `PATCH /instruments/:id/price`, `POST /instruments/refresh-quotes` | admin |
| `/transactions/*`, `/positions/*` | any authenticated user, **scoped to themselves** |
| `/users/*` | admin |

`PATCH /instruments/:id/price` is a separate route from `PUT /instruments/:id` on purpose: keeping quotes current is routine daily work while editing master data is not, so they deserve to be separately grantable and separately auditable.

**A ledger is strictly personal — including from admins.** Every transaction and position query is scoped to the caller in the db query itself. An admin's privileges cover the shared instrument master data and user accounts, *not* other people's books. Reading or deleting someone else's transaction returns **404, not 403**, so IDs cannot be probed for existence. `TestAdminSeesOnlyTheirOwnBook` and `TestAnotherUsersTransactionIsNotFound` pin this down.

**Logging & request IDs.** `main.go` configures a JSON `slog` logger as the default. `internal/middleware` adds `RequestID` (reuses an inbound `X-Request-ID` or generates a UUID, echoes it back) and `Logger` (one structured record per request). The router uses `gin.New()` + these + `gin.Recovery()` instead of `gin.Default()`. `respondDBError` logs 500s via `slog` including the request id — never `log.Printf`.

**Frontend** is a six-view SPA (vue-router: `/positions`, `/transactions`, `/instruments`, `/users`, `/account`, `/login`) plus a shared `components/PaginationBar.vue`. `frontend/src/types.ts` mirrors the Go models and is the contract between the two halves — keep it in sync when changing JSON shapes. `api/client.ts` is the only place that talks HTTP; views call `instrumentApi` / `transactionApi` / `positionApi` and hold their own local state (module-level refs, no Pinia). `session.ts` is the dependency-free source of truth for the bearer token and current user, mirrored to `localStorage` and exposed as reactive `isAuthenticated`/`isAdmin`; `api/client.ts` attaches the token to every request and calls `clearSession()` on any 401. The router guard mirrors the backend's rules as a convenience — the API enforces them.

Each view follows the same shape: `load()` / `changePage()` / `applyFilter()` plus `loading`/`error`/`success` refs, with `applyFilter` resetting `offset` to 0 and `load` stepping back a page if a deletion emptied the current one.

## Conventions

- Adding a backend resource means touching all layers: model in `internal/models` (with GORM tags, and registered in the `AutoMigrate` call in `db.Open`), CRUD methods on `db.DB`, a handler struct with a `New*Handler(s *db.DB)` constructor, and route registration in `internal/router/router.go`.
- Migrations are automatic (`AutoMigrate` on startup), which adds columns/tables but does not drop or alter existing ones; destructive schema changes must be handled manually.
- CORS is permissive (`internal/router/router.go`) for local dev; tighten before any real deployment.
- `main.go` runs the server under `http.Server` with signal-driven graceful shutdown (SIGINT/SIGTERM → `Shutdown` with a 10s drain → `db.Close`). `GET /health` calls `db.Ping` so it reflects DB connectivity.
- Code comments and all user-facing strings are in English.

## Deliberately out of scope

Cash balances and buying power, FX rates and cross-currency totals (currencies are tracked and reported separately, never converted), FIFO/specific-lot cost basis, dividends and stock dividends, splits and reverse splits (they invalidate every historical share count — a good exercise, but a step up in complexity), external market-data feeds, and multiple portfolios per user. The moving-average choice in particular is load-bearing: FIFO would require a lot table and consumption logic, and would change invariants 1 and 2 substantially.
