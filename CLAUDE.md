# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

**StockBook** — a personal portfolio ledger: a Go + Gin REST API (repo root) serving **Instrument**, **Transaction** and **Position** resources, plus a Vue 3 + TypeScript SPA (`frontend/`) that consumes it. Users record trades and cash dividends that already happened; the system derives holdings, moving-average cost, and realized/unrealized profit and loss. There is no cash balance, no order matching, and no broker integration — it is a book of record, not a trading system.

Persistence is SQLite via GORM, using the pure-Go driver `github.com/glebarez/sqlite` (no cgo). The DB file path defaults to `stockbook.db` and is overridable with the `DB_PATH` env var.

## Commands

Backend (run from repo root):

```bash
go run .                    # start API on :8080 (PORT env var overrides)
go build ./...              # build
go vet ./...                # vet
go test -race ./...         # run the test suite — ALWAYS with -race, see below
```

Backend env vars: `PORT` (default 8080), `DB_PATH` (default `stockbook.db`), `AUTH_SECRET` (HMAC key for bearer tokens — if unset a random key is generated at startup, so tokens do not survive a restart; set it in any real deployment), and `ADMIN_USERNAME`/`ADMIN_PASSWORD` (when both set and no users exist yet, an admin account is seeded on startup).

Frontend (run from `frontend/`):

```bash
npm install
npm run dev                 # Vite dev server on :5173, proxies /api -> :8080
npm run build               # vue-tsc --noEmit type-check, then vite build
npm run type-check          # type-check only
npm test                    # vitest unit tests (npm run test:watch for watch mode)
```

To work on the full stack, run the backend and `npm run dev` simultaneously; the Vite proxy (`frontend/vite.config.ts`) forwards `/api/*` to the backend, so the SPA uses same-origin relative URLs.

**Testing & CI.** `go test -race ./...` — the `-race` flag is not optional here. The concurrency tests in `internal/handlers/concurrency_test.go` are the ones that justify the compare-and-swap in the position write path, and without the race detector they are close to meaningless. Frontend tests are Vitest units colocated with their modules (`src/*.test.ts`) covering `money.ts`, `session.ts`, and `positionMath.ts` — the last is the contract test mirroring the backend's valuation rules, so changing how a position is valued means updating `internal/db/positions.go`, `positionMath.ts`, and that test together. Tests run in a plain node environment; `frontend/vitest.setup.ts` stubs `localStorage`. There are no component tests yet; adding some means switching `test.environment` in `vite.config.ts` to a DOM implementation. CI (`.github/workflows/ci.yml`) runs on pushes to master and PRs.

## Architecture

**Backend layering** (`internal/`): requests flow `router → handlers → db → models`. The `db.DB` wraps a `*gorm.DB`; it is created once in `main.go` via `db.Open(dsn)` (which opens the DB and runs `AutoMigrate`) and injected into handlers. String UUID primary keys are generated by the handlers (`uuid.NewString()` when building the model on create), not by the db layer. Handlers never touch GORM directly. The db layer translates GORM's `gorm.ErrRecordNotFound` into the sentinel `db.ErrNotFound`, which `handlers.respondDBError` (in `common.go`) maps to 404; `models.ErrInsufficientShares`, `db.ErrConflict`, `db.ErrSymbolTaken` and `db.ErrInstrumentInUse` map to 409; anything else becomes a 500. The connection pool is capped at a single connection (`SetMaxOpenConns(1)` in `db.Open`) because SQLite allows only one writer at a time.

**Money is integer minor units everywhere.** Every monetary field (`price`, `fee`, `net_amount`, `last_price`, `cost_basis`, `realized_pl`) is `int64` hundredths, never a float. The API speaks minor units; the frontend converts at the UI edge via `frontend/src/money.ts`. Share counts are whole `int` — there are no fractional shares.

**There is no FX rate anywhere, so amounts in different currencies are never added.** `Instrument.Currency` is `TWD` or `USD`, defaulting from the market (`models.DefaultCurrencyForMarket`) and overridable at creation. `GET /positions/summary` therefore returns a **slice** of `db.CurrencySummary`, one per currency the user holds, never a single grand total — summing a TWD cost basis with a USD one produces a number that means nothing. The frontend renders one card block per currency side by side. A currency becomes **locked once trades exist** against the instrument (`db.ErrCurrencyLocked` → 409): every price and cost basis recorded under it is denominated in the old currency, so switching would reinterpret the whole history rather than correct it. Instruments predating the column are backfilled from their market in `db.Open`, because an empty currency would silently drop those holdings out of every total.

### The six invariants

These are the things most easily broken by a well-meaning change. Each has tests pinning it down.

**1. `Position.CostBasis` is the total remaining cost, never a per-share average.** Storing an average would accumulate rounding error on every single trade: 3 shares at $10.00 plus 1 at $10.01 average 1000.25 cents, which is not an integer. Storing the total keeps `CostBasis` exact because it only ever gets added to and subtracted from. The average is derived for display at the UI edge (`averageCost` in `positionMath.ts`) and never persisted or returned by the API. Do not add an `average_cost` column or response field.

**2. Replaying the ledger is the definition of a position; the `positions` table is a cache of it.** `db.ReplayPosition` folds a user's transactions through `models.PositionState.Apply` in `ledgerOrder` and is the authoritative answer. `syncPosition` may take an incremental shortcut — applying just the new entry to the current row — but **only** when that entry sorts last in the ledger. An edit, a delete, or a back-dated entry landing mid-history always triggers a full replay, because moving-average cost is order-dependent and a single incremental step would compute the basis against the wrong prefix. `TestMaterializedPositionMatchesReplay` checks both paths agree across a table of sequences; any new write path must be added to it.

**3. The ledger's sort key is the triple `(traded_at, created_at, id)`.** Chronology alone is not a total order — several trades on the same day would fold in an arbitrary order and the average cost would drift between replays. `created_at` breaks same-day ties and `id` breaks same-tick ties. `isLastInLedger` compares the full triple, which is why an entry created in the same clock tick as another correctly falls back to a replay.

**4. Position writes are compare-and-swap, never read-then-write.** `writePosition` conditions its UPDATE on the `(quantity, cost_basis, realized_pl)` triple read a moment earlier — that triple is the row's version. Zero rows matched means somebody else moved it, which surfaces as `db.ErrConflict` → 409 rather than a silent overwrite. A plain conditional UPDATE (the `SET stock = stock - ? WHERE stock >= ?` trick an inventory system can use) is **not** available here: a sell releases cost in proportion to the shares leaving, so the new value depends on the old one in a way SQL arithmetic cannot express. For a holding that does not exist yet, the unique index on `(user_id, instrument_id)` turns a concurrent double-insert into the same conflict. `internal/db/cas_test.go` drives the guard directly, because the handler-level concurrency tests would otherwise pass on SQLite's single-writer serialization alone and prove nothing.

**5. Server-authoritative amounts, snapshotted symbols.** `Transaction.NetAmount` is always computed by `models.NetAmount` from quantity, price and side; a client-supplied value is ignored. `Transaction.Symbol` is snapshotted from the instrument at entry time, so renaming an instrument never rewrites history. `db.CreateTransaction` resolves the instrument inside its own transaction so it cannot be deleted between validation and the write.

**6. A realizing entry's `RealizedPL` stamp is a decomposition of the position's total, and must always add back up to it.** `Position.RealizedPL` is a running total, which cannot answer "how did last year go?" — so each sell and each dividend also stores the step it contributed. The stamp is never recomputed from quantity and price: `foldLedger` derives it by subtraction across a single `Apply` (`realizedStep`), which keeps `models.PositionState.Apply` the only implementation of the moving-average algebra. Both write paths stamp — the incremental one writes the appended entry, the replay path restamps **the whole ledger**, because changing one entry changes the average every later sell was measured against. `TestStampsSumToPositionRealized` checks the sum against the materialized position across the same table of sequences as invariant 2, and any new write path must keep that true. A buy's stamp is nil (it realizes nothing, which is not zero); a sell's or dividend's is nil only when `db.backfillRealizedPL` could not replay its holding, which `RealizedReport` counts as `UnstampedEntries` and excludes from the totals rather than folding in as zero.

### Cash dividends

`models.SideDividend` is a third kind of ledger entry beside buy and sell, not a separate resource: it goes in through `POST /transactions`, folds through `Apply` like everything else, and carries a `RealizedPL` stamp like a sell.

**A dividend is income, not a refund of what the shares cost.** It adds its payout to `RealizedPL` and leaves `Quantity` and `CostBasis` alone. The alternative convention — deducting the payout from the cost basis — is how a US return of capital is treated, and adopting it here would make an ordinary Taiwanese cash dividend quietly inflate the paper gain still showing on shares the user holds, instead of appearing as the income it is. `TestApplyDividendIsIncomeNotCostReduction` pins this down.

Its three numbers reuse the trade fields as `Quantity` = shares the payout was made on, `Price` = amount per share, `Fee` = tax withheld, which is how a dividend is announced; `NetAmount` is `q*price - fee` like a sell's (`models.NetAmount` keys off `SideBuy`, not `SideSell`, so a new realizing side gets the right sign by default). The trade form relabels those three fields rather than growing a second near-identical form.

**A dividend is deliberately not checked against the shares on hand.** It is earned on the ex-dividend date but lands weeks later, by which time the shares may have been sold; refusing that entry would decline to record money that genuinely arrived. Nothing about a dividend can run out or go negative, so there is no invariant needing the guard a sell requires — `TestApplyDividendAfterFullExit` keeps that path open.

`TransactionSide.Realizes()` is what decides whether an entry gets a stamp; use it rather than comparing against `SideSell`, so a future realizing side is picked up everywhere at once.

### Moving-average cost

The whole algebra lives in `models.PositionState.Apply` (`internal/models/position_state.go`), which is pure and has no database dependency:

```
BUY(q, price, fee):   qty += q;  cost += q*price + fee
SELL(q, price, fee):  requires qty >= q
                      costRemoved = round(cost * q / qty)   // half-up, integer only
                      realized   += (q*price - fee) - costRemoved
                      cost       -= costRemoved
                      qty        -= q
```

Buy fees join the cost basis; sell fees come off the proceeds and so reduce the realized gain. A full exit needs no rounding at all (`cost*q/q == cost`), so `CostBasis` lands on exactly 0 with no residue — `TestApplyFullExitLeavesNoResidue` is the most sensitive check that the proportional math is right, and it is worth keeping green above almost anything else here.

### Unknown is not zero

An instrument's `LastPrice` is a `*int64` maintained by hand; nil means no quote has been set. Everything downstream reports that honestly rather than substituting zero: `PositionView.MarketValue` and `UnrealizedPL` are nil, `positionMath.ts` returns `null`, and the UI renders an em dash. `PortfolioSummary` goes further — its valuation totals cover only the priced holdings, so it reports `PricedCostBasis` alongside them (making `TotalUnrealizedPL == TotalMarketValue - PricedCostBasis` an identity that always holds) and `PricedPositions` vs `OpenPositions` so the UI can say how much of the book the totals actually account for. Showing an unvalued holding as $0.00 would read as a total loss; do not "simplify" these to zero.

### Fetching quotes

`internal/quotes` fetches prices from Yahoo Finance's undocumented chart endpoint (no API key, no official support — it has broken before). `quotes.Ticker` maps `(symbol, market)` to the ticker Yahoo knows: `.TW` for TWSE, `.TWO` for TPEX, bare for NYSE/NASDAQ, and nothing for `OTHER`. Nothing outside that package knows where prices come from, so replacing the provider is a one-file job.

**Adding an instrument is not a privileged act.** `POST /instruments` and the search that feeds it are open to any authenticated user, and rate-limited because both reach the provider. Gating them behind an admin would block a user from recording a trade in a stock nobody had entered yet — a harder stop than the stale quotes that opened the refresh endpoint — and what gets added is a listing the provider has already verified, so it cannot be junk. Renaming and deleting stay with admins, since those change entries other people are already trading against.

**An instrument cannot exist unless the provider can price it.** `POST /instruments` accepts only `{symbol, market}`; the handler resolves the ticker, fetches a quote, and fails the request if that fails — `ErrNoQuote` becomes 422 (the caller picked a symbol the provider does not know and can pick another), anything else 502 (the provider is unwell and they can only wait). The name, currency and opening price all come from the fetched quote rather than the caller, for the same reason transaction amounts are computed server-side: the authority on what an instrument is called and what it trades in is the source that quotes it. Three things about the fetched quote are then checked, and they are separate on purpose: the instrument must be **holdable** (`quotes.IsHoldable` — an index or a futures contract prices perfectly well and cannot be owned), the exchange must **cross-check** against the requested market via `FromTicker`, and the currency must be the one that market trades in. The currency check is the backstop for a foreign listing the provider names without a suffix, which the cross-check cannot see because a bare ticker reads as a US one by design.

This is what makes an unquotable instrument **unrepresentable** rather than merely discouraged. Every quote problem so far came from that state existing — a symbol the provider had never heard of, sitting in the master data looking perfectly normal, whose only symptom appeared much later as a quote that never arrived. It also means a new instrument arrives already priced, so its holdings can be valued the moment a trade is recorded.

`PUT /instruments/:id` **only renames.** Symbol and market are identity and decide how the instrument is priced — editing them is exactly what filed 2330 under TPEX — and currency belongs to the provider and is baked into every cost basis recorded since. A listing entered wrongly is deleted and re-added, which `ErrInstrumentInUse` already refuses once trades reference it. The display name stays editable because a provider's capitalised English name is often not what a user wants to read.

`PATCH /instruments/:id/price` survives as the escape hatch for a provider outage but has no UI: prices are the provider's job now.

**Finding instruments.** `GET /api/v1/instruments/search?q=` (any authenticated user, rate-limited 30/min) proxies the provider's search and returns only candidates this system can model, pre-translated into the symbol, market and currency that would be stored, plus an `exists` flag for symbols already in the master data. `quotes.FromTicker` is the exact inverse of `quotes.Ticker` — a `TAI` result named `2330.TW` becomes symbol `2330` on `TWSE` — and `TestFromTickerRoundTripsWithTicker` pins that correspondence down, because a symbol stored from a search result that did not round-trip would be looked up under a name the provider does not use. Non-holdable types (indices, futures, currency pairs, mutual funds) are dropped rather than offered as rows that cannot be added.

**`FromTicker` asks "can we look this up again exactly as the provider names it?", not "do we recognize this exchange?".** The distinction is load-bearing, and getting it wrong is what hid every NYSE Arca ETF — VOO, SPY, VTI, IWM, GLD — from search *and* from the manual create form, since both consult this one function. The rule now:

- a suffix this package appends itself (`marketSuffix`: `.TW`, `.TWO`) means Taiwan, and it must agree with the exchange reported alongside it — a `.TW` ticker filed as TPEX would be re-fetched as `2330.TWO`, which does not exist;
- any **other** suffix belongs to a venue this system cannot address (`.DE`, `.L`, `.HK`, `.MX`) and is refused;
- a **bare** ticker is a US listing, whichever venue carries it. `usMarket` names the Nasdaq tiers exactly and falls back to `NYSE` for everything else (`PCX` NYSE Arca, `BTS` Cboe, `ASE` NYSE American, and whatever the provider codes next).

That fallback accepts a small labelling imprecision — SPY is filed as NYSE though it trades on Arca — in exchange for never silently dropping a real holding again. It costs nothing operationally: `Ticker` sends a bare symbol for both US markets, so the market only affects the label. `marketSuffix` is the single table both directions read, so the round trip cannot be broken by editing one side.

The assumption underneath is that the provider suffixes every non-US listing. If that ever stops being true, the currency check on the create path is what still catches it.

This is the intended way to add an instrument, and it exists because a hand-typed symbol has no guarantee the provider knows it: the mistake surfaces much later as a quote that never arrives, which is the failure mode both `ExchangeSuffix` validation and the ticker-in-the-error message were added to soften. A symbol chosen from the provider's own answer is quotable by construction. The manual create form remains for anything the provider does not list.

The provider matches symbols and English names only — a query in Chinese returns nothing, which is a limit of the source rather than the endpoint.

`POST /api/v1/instruments/refresh-quotes` drives quote refreshing. It is a deliberate, caller-triggered action rather than a background ticker, because **a background job has nowhere to return errors to** — a failed symbol would land in a log nobody reads. The endpoint returns 200 with a per-instrument result (`updated` / `skipped` / `failed`), each failure carrying **the provider's own wording** ("No data found, symbol may be delisted"), which is the only actionable diagnostic for a bad ticker. A partial failure is not an error for the run: one delisted symbol must not stop the other twenty from updating. To schedule it, point cron at the endpoint.

**It is open to any authenticated user, not just admins.** The holdings page exists to show unrealized profit and loss, which is dead without a current price; gating refresh behind an admin would leave every other user unable to do anything about a stale book, and a market price is shared objective data rather than something a caller owns. Two things keep an open endpoint from becoming a way to hammer a third party: instruments checked within `quoteFreshness` (15 minutes) are skipped entirely, so pressing refresh twice costs one round of traffic, and the route carries `middleware.RateLimit(6, time.Minute)`. Skipped-as-current instruments are counted in `fresh` but deliberately left out of `results` — on a repeat press they would be the whole list and none of them is actionable. Setting a price *by hand* (`PATCH /:id/price`) remains admin-only, as does everything else about the master data.

**The two quote timestamps are not interchangeable.** `Instrument.PriceUpdatedAt` is when the price was good for (the market timestamp the provider reported) and drives the staleness a user sees; `Instrument.QuoteCheckedAt` is when the provider was last asked and drives the freshness skip. Merging them breaks one job or the other: `isQuoteFresh` reading `PriceUpdatedAt` would find every quote stale outside trading hours and refetch the whole book on every press, while showing `QuoteCheckedAt` to a user would make a Friday close fetched on Monday look like a live price. `db.QuoteUpdate` carries both, each defaulting to now.

Two rules protect the book from the provider:

- **A failed fetch changes nothing.** The instrument keeps its previous quote *and both its timestamps*, so the staleness rendered by `quoteAge()` in the UI stays truthful and a symbol whose market was just corrected is retried immediately rather than being suppressed for 15 minutes. Restamping a failed refresh would make a stale price look fresh; writing a zero would make it look worthless.
- **A currency mismatch is a failure, not a price.** If the provider quotes an instrument in a currency the book does not have on file, the fetch is reported as failed and nothing is written — adopting it would reinterpret every cost basis already recorded. Only an instrument with *no* currency yet adopts the provider's (`db.SetInstrumentCurrency`, which refuses to overwrite).

Stored quotes carry the **market timestamp the provider reported**, not the moment of the request (`db.UpdateInstrumentPrice` takes an `asOf`), so age shown to a user is the price's own age. Hand-entered quotes pass nil and are stamped now.

`router.New` takes a `handlers.QuoteFetcher`; it may be nil, in which case the refresh endpoint reports that quote fetching is not configured. Tests pass a stub — **no test ever reaches the network**, and `internal/quotes/yahoo_test.go` serves recorded payloads from an `httptest.Server`.

**Deletes and edits can be refused.** Removing a buy that a later sell drew on punches a hole in history: the replay hits `ErrInsufficientShares`, the whole transaction rolls back, and the API returns 409 with a message naming the offending entry (`insufficient shares: sell 1000 2330 on 2026-07-03`). Shrinking a buy below what a later sell consumed is refused the same way. This is the payoff of the replay architecture — the ledger can never be left in a state its own rules reject.

### Reporting realized results

`GET /api/v1/reports/realized?from=&to=` (`internal/db/reports.go`) answers what the caller banked over a period, by summing the stamps from invariant 6. It returns a **slice, one entry per currency** with a per-instrument breakdown inside it — the same rule `PortfolioSummary` follows, for the same reason. The report is not paginated: it is a summary, so it returns `{"data": [...]}` with no `pagination` block.

**Trading and dividends are reported apart as well as together.** `TradingPL` is what the sales banked, `Dividends` is what was paid out for holding, and `RealizedPL` is their sum. They are taxed differently in most places, and a book that lost on price while making it back on income must not read as a flat year. `Proceeds` and `Cost` describe the sales alone, so the identity to check is `TradingPL == Proceeds - Cost`, **never** against the combined total. `Cost` is reported rather than left to be inferred because it is what a tax form asks for next to the proceeds, and it is not recoverable from the ledger alone since it comes from the average held at the moment of each sale. For the same reason the UI's return percentage is measured against `TradingPL`: dividends are earned by holding shares, not by selling them.

**A bare `to=YYYY-MM-DD` covers the whole of that day.** `handlers.parseDateRange` stretches a date-only upper bound to the last instant of it, because `traded_at <= 2026-12-31` means midnight and would drop every trade made on the closing day of the range — a yearly report omitting its own last entry. `GET /transactions` shares the helper, so its `?to` behaves the same way. Bare dates are read as UTC, which is the calendar the rest of the system speaks: the trade form stores a chosen date at **noon UTC** precisely so the day a trade belongs to does not depend on the reader's zone, and the ledger displays it by slicing the first ten characters off the UTC timestamp.

### Money-weighted return (XIRR)

`GET /api/v1/reports/returns` (`internal/db/returns.go`) answers *how fast* the book grew, which no other figure here can. A gain-over-cost percentage is blind to time and to size: doubling 10,000 over five years and doubling 1,000,000 over one both read as `+100%`, and a well-timed second purchase counts for no more than the first. XIRR weights every dollar by how long it was actually at work, which is what makes a book comparable with another book, or with a savings rate. It returns a **slice, one entry per currency**, for the same reason every other total does.

The cash flows *are* the ledger, seen from the user's pocket — a buy is money out, a sale or dividend is money in — plus **one final payment in at `asOf`: the market value of what is still held.** Without that closing flow every unsold share would measure as money that never came back. `ReturnsReport` takes `asOf` as a parameter (the handler passes `time.Now()`) purely so the arithmetic is testable against fixed dates.

**The period is always since inception, and the endpoint deliberately takes no `from`/`to`.** A return over a *window* needs the portfolio's market value on the day the window opened, and this system stores only each instrument's current quote — there is no price history, so the book's value on any past date is not recoverable. Accepting bounds would answer a different question than the one asked. This is the single clearest thing a `price_history` table would unlock, along with an equity curve, drawdown and a benchmark comparison.

**An open holding with no quote takes its entire history out of the report** — its purchases along with its unknown value. This is the "unknown is not zero" rule applied to a figure that spans history rather than a moment, and the two alternatives are both worse: valuing it at zero shows the holding as a wipeout, and keeping its buys while dropping only its ending value reports *exactly the same wipeout* with nothing to say anything was missing. Omitting the instrument answers a smaller question truthfully, and `PricedPositions` against `OpenPositions` is what tells the caller how much of the book that is — the same pair `CurrencySummary` reports. A **closed** holding needs no quote and is always counted: its flows are complete and its ending value is genuinely zero.

`models.XIRR` (`internal/models/xirr.go`) is pure, has no database dependency, and is **actual/365**, the convention every published XIRR uses — matching it beats being astronomically right, because a number the user can reconcile against a broker statement is worth more than one that agrees with nothing. The root is found by **bisection, not Newton-Raphson**: a ledger with flows in both directions gives the present value more than one turning point, and a derivative step from a bad guess leaves the domain — Newton's divergence is the classic source of a spreadsheet's `#NUM!`. Bisection cannot diverge, needs no starting guess, and the whole search is a few hundred passes over a list built once per page load.

**The rate crosses the wire as integer basis points** (`XIRRBps`, 1234 = 12.34%), for the reason every amount crosses it as integer minor units: the rounding is decided once, on the server. It is a `*int64` and is **nil, never 0**, when no rate could be found — `Unavailable` then carries the reason in the user's own words, because a book that cannot be measured has not broken even. The three refusals (`ErrOneDirection`, `ErrSameInstant`, `ErrNoRate`) are separate errors so each can say what actually went wrong.

The UI puts this on `/positions` rather than under Realized, because the closing figure of the calculation is the market value of current holdings — exactly what the cards there already show.

**List endpoints are paginated and sortable.** All list endpoints take `?limit` (default 20, max 100), `?offset`, `?sort`, and `?order`, parsed by `handlers.parseListOptions` into a `db.ListOptions`. Response shape is `{"data": [...], "pagination": {limit, offset, total}}`; single resources are `{"data": ...}` and errors `{"error": "..."}`. **Sorting is SQL-injection-safe by construction:** `db.orderClause` only emits a column name present in a per-resource allowlist (`instrumentSortColumns` / `transactionSortColumns` / `userSortColumns`), else falls back to the default. The position list spans a join, so it has its own `positionSortColumns` mapping sort keys to *qualified* column names — needed both to disambiguate `updated_at` (present on both tables) and as the same injection guard. Never interpolate `ListOptions.Sort` into a query directly.

**Authentication & authorization.** Accounts live in a `users` table (bcrypt `PasswordHash`, `Role` of `user`/`admin`). `internal/auth` provides bcrypt helpers and a `Manager` that issues/verifies bearer tokens — base64url JSON claims joined by `.` to an HMAC-SHA256 signature (key from `AUTH_SECRET`). Signature/expiry checks are stateless, but `middleware.authenticate` then loads the account from the DB (via the `middleware.UserSource` interface) and requires that it still exists and that the token's `token_version` claim matches `User.TokenVersion` — so deletions, role changes and password changes take effect immediately. The identity placed in the Gin context comes from the DB record, not the token claims. `POST /api/v1/auth/register` always creates a **user** (clients can never self-assign a privileged role); `POST /api/v1/auth/login` is rate-limited per client IP (10/minute, in-memory fixed window, per-process). Admin-only `/api/v1/users` endpoints provision, list, re-role and delete accounts; an admin cannot change or delete their own account, so they cannot lock themselves out.

**Route gating** (`internal/router/router.go`):

| Routes | Access |
|---|---|
| `GET /instruments`, `GET /instruments/:id` | any authenticated user (needed to enter a trade) |
| `POST /instruments`, `GET /instruments/search` | any authenticated user, rate-limited |
| `PUT/DELETE /instruments/:id`, `PATCH /instruments/:id/price` | admin |
| `POST /instruments/refresh-quotes` | any authenticated user, rate-limited 6/min per IP |
| `/transactions/*`, `/positions/*`, `/reports/*` | any authenticated user, **scoped to themselves** |
| `/users/*` | admin |

`PATCH /instruments/:id/price` is a separate route from `PUT /instruments/:id` on purpose: keeping quotes current is routine daily work while editing master data is not, so they deserve to be separately grantable and separately auditable.

**A ledger is strictly personal — including from admins.** Every transaction and position query is scoped to the caller in the db query itself. An admin's privileges cover the shared instrument master data and user accounts, *not* other people's books. Reading or deleting someone else's transaction returns **404, not 403**, so IDs cannot be probed for existence. `TestAdminSeesOnlyTheirOwnBook` and `TestAnotherUsersTransactionIsNotFound` pin this down.

**Logging & request IDs.** `main.go` configures a JSON `slog` logger as the default. `internal/middleware` adds `RequestID` (reuses an inbound `X-Request-ID` or generates a UUID, echoes it back) and `Logger` (one structured record per request). The router uses `gin.New()` + these + `gin.Recovery()` instead of `gin.Default()`. `respondDBError` logs 500s via `slog` including the request id — never `log.Printf`.

**Frontend** is a six-view SPA (vue-router: `/positions`, `/transactions`, `/reports`, `/users`, `/account`, `/login`) plus a shared `components/PaginationBar.vue`. `/reports` (nav label **Realized**) picks a period with year chips plus two date fields and renders one block per currency; the ledger carries the same numbers per row, showing an em dash on a buy rather than `$0.00`. The annualized return sits on `/positions` instead, as a fifth card in each currency block — it is measured since inception, so a period picker would falsely appear to filter it, and its closing figure is the market value that page already shows. `frontend/src/types.ts` mirrors the Go models and is the contract between the two halves — keep it in sync when changing JSON shapes. `api/client.ts` is the only place that talks HTTP; views call `instrumentApi` / `transactionApi` / `positionApi` and hold their own local state. **There is no instruments page, and no separate add step.** An instrument only exists to be traded, so `components/InstrumentPicker.vue` — the trade form's instrument field — *is* the search: typing filters what has already been traded (client-side, instant, since trading the same handful of stocks repeatedly is the common case) and, after a 400 ms pause, queries the provider for the rest. Choosing a result that is not on file yet creates it on the way through, which is invisible apart from the form filling in. Making that a second explicit action would turn picking a stock into managing master data. Quote refreshing lives on `/positions`, where the numbers it feeds are shown. `instrumentApi.rename` and `.remove` have no UI; they remain callable admin-only endpoints (module-level refs, no Pinia). `session.ts` is the dependency-free source of truth for the bearer token and current user, mirrored to `localStorage` and exposed as reactive `isAuthenticated`/`isAdmin`; `api/client.ts` attaches the token to every request and calls `clearSession()` on any 401. The router guard mirrors the backend's rules as a convenience — the API enforces them.

Each view follows the same shape: `load()` / `changePage()` / `applyFilter()` plus `loading`/`error`/`success` refs, with `applyFilter` resetting `offset` to 0 and `load` stepping back a page if a deletion emptied the current one.

## Conventions

- Adding a backend resource means touching all layers: model in `internal/models` (with GORM tags, and registered in the `AutoMigrate` call in `db.Open`), CRUD methods on `db.DB`, a handler struct with a `New*Handler(s *db.DB)` constructor, and route registration in `internal/router/router.go`.
- Migrations are automatic (`AutoMigrate` on startup), which adds columns/tables but does not drop or alter existing ones; destructive schema changes must be handled manually.
- CORS is permissive (`internal/router/router.go`) for local dev; tighten before any real deployment.
- `main.go` runs the server under `http.Server` with signal-driven graceful shutdown (SIGINT/SIGTERM → `Shutdown` with a 10s drain → `db.Close`). `GET /health` calls `db.Ping` so it reflects DB connectivity, and reports `started_at`, `uptime` and `revision`. Those exist to answer "is the server running the code I just wrote?" — `go run .` does not reload on edit, and a stale process serving an old contract is indistinguishable from a bug in the new one until you can see it started before the change. `revision` is only stamped for built binaries, so `started_at` is the signal to trust.
- Code comments and all user-facing strings are in English.

## Deliberately out of scope

Cash balances and buying power, FX rates and cross-currency totals (currencies are tracked and reported separately, never converted), FIFO/specific-lot cost basis, **stock** dividends, splits and reverse splits (they invalidate every historical share count — a good exercise, but a step up in complexity), automatic dividend fetching (the provider's chart endpoint does carry `events=div,split`, so this is a natural next step rather than a closed door), and multiple portfolios per user. The moving-average choice in particular is load-bearing: FIFO would require a lot table and consumption logic, and would change invariants 1 and 2 substantially.
